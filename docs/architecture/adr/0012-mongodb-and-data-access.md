# ADR-0012: MongoDB with the native driver and a tenant-scoped data-access layer

- **Status:** Accepted (database directed by the maintainer)
- **Date:** 2026-10-16
- **Supersedes:** [ADR-0002](0002-postgresql-and-prisma.md)
- **Amends:** the enforcement mechanisms named in [ADR-0004](0004-authentication-and-sessions.md) (session storage) and [ADR-0006](0006-versioned-approvals.md) (partial unique indexes)
- **Related:** NFR-001–003, BR-009, BR-010, BR-018, BR-023, BR-028, BR-030, SEC-004

## Context
The maintainer has directed MongoDB. ADR-0002 relied on PostgreSQL features: foreign keys, composite tenant FKs, partial unique indexes, row locks, triggers and table grants. Several business invariants must be preserved with MongoDB mechanisms instead.

## Decision
1. **MongoDB is the only datastore.** It must run as a **replica set**, because multi-document transactions are required. Local development and CI use a single-node replica set.
2. **Native MongoDB Node.js driver, no ODM.** Document shapes are defined as TypeScript types plus Zod schemas inside `apps/api`. Each collection also gets a `$jsonSchema` validator applied by migrations as defence in depth.
3. **Data-access layer (`apps/api/src/platform/db`):**
   - Only `platform/db` imports `mongodb`. Module repositories receive typed wrappers.
   - `TenantCollection<T>` automatically adds `workspaceId` to every filter, insert and aggregation `$match`. It rejects attempts to set or override `workspaceId`. Raw collections are not exported.
   - `withTransaction(fn)` runs a callback in a session with majority write concern and snapshot read concern. It retries transient transaction errors through the driver's `withTransaction`.
4. **How invariants are kept** (replacing the Postgres mechanisms):

   | Invariant | MongoDB mechanism |
   | --- | --- |
   | Tenant isolation (SEC-004) | `workspaceId` on every tenant document. `TenantCollection` scoping. Every index is prefixed with `workspaceId`. Referenced documents are loaded with the same `workspaceId` before linking |
   | One open version, one approved version (BR-009, BR-013) | Versions are embedded in the `changeRequests` aggregate. Conditional updates on `openVersionNumber` and `approvedVersionNumber` |
   | One decision per version, immutable (BR-010, BR-014) | Insert-only `approvals` collection with a unique index `{workspaceId, changeRequestId, versionNumber}`, plus a conditional CR update in the same transaction |
   | One non-void invoice per entry (BR-018) | `billableEntries.invoiceId` is set by a conditional update (`invoiceId: null`) inside the invoice transaction |
   | Gapless invoice numbers (BR-023) | `$inc` on the workspace counter inside the issuing transaction. An aborted transaction rolls the increment back |
   | Audit atomicity (BR-028) | The audit insert happens in the same transaction |
   | Append-only audit and approvals (NFR-003) | The repository exposes no update/delete. In production, a custom DB role grants only `find` and `insert` on `auditEvents` and `approvals` |
   | No hard delete of referenced records (BR-030) | Services check references. Repositories expose no delete for these collections |
   | Optimistic concurrency (`If-Match`) | `rowVersion` is part of the update filter. Zero matched documents means `412` |

5. **IDs** are UUIDv7 strings in `_id`, generated by the application, which keeps API IDs uniform. ObjectIds are not exposed.
6. **Money** is stored as BSON Int64 and handled as `bigint` in the API (ADR-0007). Configuring the driver for `bigint` round-tripping is verified in M1. Decimal128 is not used.
7. **Migrations:** versioned scripts in `apps/api/migrations/` are applied by a small in-repo runner. The runner records applied scripts in a `schemaMigrations` collection. Scripts create collections, validators and indexes, and perform backfills.
8. **Sessions and idempotency keys** are collections with TTL indexes.

## Alternatives considered
- **Keep PostgreSQL (ADR-0002):** stronger relational guarantees, but not the maintainer's choice.
- **Mongoose:** popular and familiar, but it creates a second schema system next to Zod, and its middleware and hidden behaviour complicate transaction reasoning. Rejected for the MVP.
- **Fully normalised collections (versions as separate documents):** closer to the old relational model, but needs more transactions to keep CR-level invariants. Embedding versions makes the state machine a single-document atomic update.
- **Prisma with MongoDB:** removes the ORM familiarity benefit, adds limitations and needs replica sets anyway.

## Rationale
The CR aggregate (CR + versions) maps naturally to a document. Single-document conditional updates give race-free state transitions. Transactions cover the cross-collection cases (approval + audit, invoice issue). An explicit tenant-scoped wrapper replaces the database-level FK safety net with a code-level one that tests can check.

## Consequences
- There are no database-enforced foreign keys. Referential integrity is a service responsibility and must be covered by integration tests.
- A replica set is required everywhere, including local and CI.
- CR documents grow with versions. This is bounded and small (far below the 16 MB document limit), but very long revision histories should be monitored.

## Security and operational implications
- The app connects as a least-privilege user with no `dropDatabase` and no admin roles.
- MongoDB must not be exposed publicly. Use TLS for remote connections.
- Back up with `mongodump`/`mongorestore` or the provider's snapshots, and rehearse restores (NFR-016).
- Query filters are built only from validated values. Raw user objects are never passed as filters, which prevents operator injection such as `{"$ne": null}`.
